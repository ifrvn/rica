# Rica 插件架构与最佳实践

Rica 支持随宿主交付的内置插件、通过部署清单安装的受信 npm 包，以及通过 HTTP 接入的独立服务。先选进程和数据的边界，再选能力。实现签名以 [SDK 源码](../../packages/plugin-host/sdk.ts) 为准，调用参数和示例见[第三方 SDK](08-package-sdk.md)。

## 接入方式

| 方式 | 如何装配 | 适用场景 |
| --- | --- | --- |
| 内置插件和实现 | 工作区包随 Rica 发布，由 API、Worker 和控制台入口装配。插件中心管理已交付的部署项。 | 外部模型提供方、模拟适配器、Newbi 等需要内置 UI 或宿主专用流程的实现。 |
| 受信 npm 包 | 在部署目录安装固定版本，使用 `RICA_PLUGIN_MANIFEST` 声明包。API、Worker 和迁移任务按各自职责加载。 | 角色级管理读写、账号登记、后台任务、统一活动、保留期和声明式控制台。 |
| 独立服务 | 使用 `RICA_REMOTE_PLUGIN_MANIFEST` 配置令牌变量、账号范围和能力。服务通过 HTTPS 使用事件与任务协议。 | 独立部署、独立数据库、隔离依赖或运行环境的读取与计算。 |

模拟适配器与模型提供方沿用[内置运行时接口](02-runtime.md)。包内第三方能力由 SDK 声明，完整自定义管理路由与专用 Vue 入口用于[内置装配](03-management.md)。独立服务可发布和订阅活动摘要，也可领取任务并记录回执。真实平台的写操作遵循[平台执行许可](04-platform-safety.md)。

## 宿主和插件各自负责什么

| 宿主负责 | 插件负责 |
| --- | --- |
| 浏览器会话、角色权限、身份与账号绑定、管理审计、宿主命令的幂等 | 外部协议、拥有的数据、输入与输出校验、凭据保存和远端核验 |
| 根据进程选择能力，检查插件版本和契约，启动、取消、停机 | 声明能力、启动前检查配置、限制并发、停止领取和释放资源 |
| 提供受限业务接口，按用途准备模型上下文，合并活动和状态投影 | 对本地记录继续按角色、账号和绑定范围筛选，返回公开摘要 |
| 审批、许可、授权撤销和对账状态 | 按平台能力发起获准操作，使用同一幂等键恢复原尝试并保存回执 |

npm 包与宿主共享进程信任边界。数据库角色约束连接权限，独立进程和服务凭据提供额外隔离。需要隔离的实现优先走 HTTP 接口。正式环境由部署流程切换版本，插件中心提供内置项配置、启停和版本预览。

## 数据库与跨边界查询

插件的业务表、索引和约束由包维护。一个普通 Prisma 插件通常用一份 `prisma/schema.prisma`、一个 `prisma/migrations/` 和一个 `./rica/prisma` 导出。发布包包含生成的独立 Prisma Client。普通 CRUD 用模型方法，函数、触发器和数据库角色授权写进迁移 SQL。

| 需求 | 接口 |
| --- | --- |
| 查询或更新插件自己的业务表 | 用插件的 Prisma Client，运行账号只授予所需表和列权限。 |
| 显示宿主账号信息或插件公开资料 | 通过 `services.readAccounts(ids)` 或已声明的资料视图获取字段。先完成宿主授权和分页，再按 ID 批量补充投影。 |
| 统一活动列表，需要全局筛选、排序和分页 | 同库使用 `activity` 声明的窄视图，独立服务按事件 ID 幂等发布摘要。宿主按角色和账号归属合并，并使用包含微秒时间的稳定游标。 |
| 登记或删除账号、执行审计写命令，需要原子提交 | 同库用 `accounts` 或 `commands` 声明受限 SQL 函数，由宿主在同一授权事务中调用。将外部网络核验放在事务前，写入时重查权限与绑定。 |
| 跨库读写或异步工作 | 使用事件、任务及回执协议。保存处理游标和幂等键，按重试设计，不依赖跨库事务。 |

把角色 ID、账号 ID 和绑定版本作为协议字段。跨模块读取优先使用宿主能力、窄视图或事件摘要，避免直接依赖另一模块的私有表结构。宿主 Client 和各插件 Client 分别生成。

[Newbi](../../plugins/newbi/README.md#开发与部署) 是内置样例。七张业务表位于 `rica_plugin_newbi`，模型与迁移各只有一套。内置和清单模式共用数据库对象与活动视图，`rica migrate` 沿用 `rica_bootstrap_newbi` 记录迁移。普通模型查询使用 Newbi Client。涉及账号绑定、审批、租约或发送许可的事务使用宿主授权和受限函数。

## 开发最佳实践

1. **按能力设计包**。用稳定的插件 ID 区分 npm 包名、组件 ID 和发布版本。先声明最小的 SDK 能力，使用固定版本与锁文件部署。入口模块只声明能力，把数据库连接、计时器和订阅放进受管生命周期。
2. **让数据库权限与操作匹配**。第三方插件分别配置迁移和运行登录。运行身份只得到所属 schema 的最小权限。使用 `SECURITY DEFINER` 时限定对象 schema、固定 `search_path`、撤销 `PUBLIC` 权限并逐项授权。凭据只注入需要它的进程，摘要、配置响应和日志只保留可公开字段。
3. **保持授权、数据与失败语义一致**。在事务内重查绑定和授权版本。命令、事件和回执都使用稳定幂等标识。多个 Worker 并行时按租约或数据库约束去重。未知的外部结果先核对原请求与回执，继续使用原幂等键。
4. **验证按安装方式覆盖真实边界**。在隔离空库验证初始化和重跑，再用上一版本的测试数据验证升级。安装发布包核对导出、生成的 Client 和 SQL 文件。用受控夹具测试跨角色、撤权、并发、超时、部分初始化失败、停机和重新领取。详见[验证与发布](06-verification-release.md)。
5. **把配置、进程就绪和实际调用分开观测**。记录插件、组件和契约版本。用结构化结果诊断失败，区分服务尚未就绪、授权拒绝及外部结果未知。控制台状态和公开 API 复用相同的业务枚举。

系统层约束和验收编号见[系统设计规范第 17 章](../多平台多身份%20AI%20虚拟角色认知与自主行为系统设计规范.md#sec-17)。
