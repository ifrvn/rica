## M1 可靠角色基础

目标是在隔离的模拟环境中，用一个核心角色、三个身份、两个模拟平台完成「入站 → 授权召回 → 决策与草稿 → 审批 → 模拟回执 → 审计」。外部自动发布保持关闭。

| 工作包 | 依赖 | 交付 | 验收 |
| --- | --- | --- | --- |
| **M1.1 上下文和记忆授权** | 已落地的身份绑定与 Worker | 补齐会话、联系人、记忆、来源和授权的最小关系模型。以固定 Run 绑定构建检索上下文。数据库先按归属、来源状态、用途、受众、期限和授权过滤，再返回允许排序的候选。撤权推进 `authEpoch`，并使受影响的派生内容失效。配置独立数据库运行角色和 RLS。 | 验证四层作用域、组合外键、公司机密隔离、用途分离和撤权后的拒绝。先通过 AT-02、AT-03 的检索部分。 |

## M1.6 验收记录

| 验收项 | 结果 |
| --- | --- |
| 三身份、双模拟平台 | 后端验收通过。同一主题和投递键从两个适配器进入三个独立账号，经事务出箱和 Worker 生成三种语气的草稿。Hono 审批核对每条提案的身份、账号和会话。审批前回执为 0，批准后重复执行仍各有一条本地回执，回放显示同一核心版本和各自的身份与账号。 |
| Vue 审批到模拟回执 | Chrome 中用生产构建和模拟身份提供方验证。无效令牌被拒绝，390 像素宽度无横向溢出，键盘可批准。审批员核对三条提案的身份、账号、受众、正文与 AI 披露。三条审批均由浏览器提交，执行器各生成一条原账号回执，回放均为 SIMULATED。 |
| 10 万条记忆、10 并发检索 | 通过该数据集的 300 ms 门槛。退出验收复测的 100 次采样全部成功，P50 222.5 ms、P95 266.6 ms、最大值 274.5 ms。优化前预热批次 10 次全部触发 2 秒数据库语句超时（SQLSTATE `57014`）。 |

检索环境为 Windows 上的 Node.js 26.12.1，Docker Linux 虚拟机报告 12 个逻辑 CPU 和约 13.6 GiB 内存，运行 PostgreSQL 18.6 和 Redis 8.10.3。夹具为同一角色的 10,000 条已批准 CORE 记忆和每个身份 30,000 条 IDENTITY 记忆，约 1% 的 ASCII 短文本匹配同一主题，每条记忆有公开来源，采用原生作用域授权。计时覆盖运行绑定加载、数据库授权候选查询和应用重排。正常完成时丢弃首批预热，再采样 10 批共 100 次，无模型调用。夹具准备和清理单独使用管理事务，运行角色的 2 秒数据库语句超时仍生效。

执行计划曾显示单次数据库候选扫描约 1.4 秒，重排尚未开始。优化后，行级安全策略先排除无可见授权的其他身份候选及无法命中关键词的 ASCII 候选，再按原用途、期限、受众和完整来源集合验证授权。非 ASCII 文本和当前会话证据继续由原排序器判断。回放只按已有快照的证据 ID 查找并重验。这里的延迟数据适用于上述 ASCII 夹具。

迁移只调整授权函数和读取策略。旧版应用可继续使用新迁移后的数据库，旧版请求缺省按未启用关键词预筛选处理。

在独立测试库设置 `DATABASE_URL` 和 `MIGRATION_DATABASE_URL`、应用迁移后，用 PowerShell 单独运行基准。超时、结果越权或 P95 超过 300 ms 时命令返回失败。

```powershell
$env:RICA_RECALL_BENCHMARK = '1'
pnpm exec tsx --test --test-name-pattern='measures authorized recall' scripts/inbound.integration.test.ts
Remove-Item Env:RICA_RECALL_BENCHMARK
```
